# WP-C3 — the atlas gets its own page: `/map` becomes `/atlas`

The blueprint's WP-C3 row is the contract:

> Flat map default; filter rail; place panel; list view replaces `/regions`.
> Stop drawing relation type `family`. Generate place pages only for places
> with one or more dishes.

Blueprint: `~/projects/gustale-state/docs/blueprint/2026-11-15/GUSTALE-BLUEPRINT-2026-11-15.md` line 379.
Mockup: `mockups/proposed-Atlas.png`.

---

## 1. `/map` → `/atlas`, and the map is FLAT by default

`pages/map.astro` → `pages/atlas.astro`. The globe is no longer the default: the
map opens **flat**, and the globe is the secondary view in the switcher.

The old page was a map with no way to find anything on it. The new one is a
**single client island** (`AtlasIsland.tsx`) that owns the filter state, the
selection, the URL and the view switcher together — so the rail, the map and
the place panel can never disagree with each other.

`/map` redirects to `/atlas` (301, `nginx.conf`, generated by
`scripts/generate-redirect-rules.mjs`).

## 2. The filter rail

The mockup's left rail: a **text search** over places and dishes, and three
**dropdowns**.

**Which three?** The mockup says *Period / Ingredient / Family*. Two of those
do not exist as vocabularies in the data:

| dropdown | why |
|---|---|
| **Family** | `dish_dish_families` → `dish_families`; 92 of the 121 map dishes carry one |
| **Technique** | `dish_dish_techniques` → `dish_techniques`; 117 carry one |
| **Course** | `dish_dish_courses` → `dish_courses`; 116 carry one |

- **Period** is not a vocabulary. A dish carries an origin *date range*
  (`origin_date_earliest`/`latest`), and only 8 published dishes have one — a
  dropdown of eight values, six of them empty, is a control that cannot filter.
- **Ingredient** is possible but only **1** of the 121 map dishes has an
  ingredient recorded, so it would be a dropdown offering one option.

So the third dropdown is **Course**, the nearest thing the data actually has.
The counts that make this defensible are in the API's own comments.

The rail also carries the mockup's three **relationship** checkboxes —
Associated places, Documented influence, Resemblance — over the
`RelationshipLayer`'s vocabulary.

**The facets come from the API, not from the client.** `/api/dishes/map`
now returns the vocabulary *and* the counts, because a client cannot derive a
facet list from dish fields that do not exist. The three queries join on
`value_id` (the junction tables' real column — `dish_id`/`value_id`, not
`dish_id`/`technique_id`), and the technique facet is restricted to
`dt.status = 'active'`.

## 3. The place panel

The mockup's right panel: the selected place's dishes, its dish groups, the
threads that pass through it, and a link to its place page.

- The **dish count is the place's full published total**, not the current
  filtered subset — the panel describes the place, not the filter.
- The **threads through a place** are counted as distinct `dish_lineages`
  across that place's published dishes. `lineages` has **no status column**, so
  every lineage is curated; publication filtering belongs on the dish.
- The API's place slug is **authoritative**. The derived slug is only a
  loading fallback.

## 4. The list view replaces `/regions`

`pages/regions.astro` → `pages/places/index.astro`. `/regions` redirects to
`/places`.

The **Map / List / Timeline** switcher lives in the atlas island. *Timeline* is
the blueprint's WP-C4 work and is not built here — the control is there and
it does not lie about what it does.

## 5. Place pages move to `/places/[slug]`

`pages/place/[slug].astro` → `pages/places/[slug].astro`. `/place` redirects to
`/places`.

**Place pages are generated only for places with one or more dishes.** That
rule was already in `getStaticPaths` — it excluded the places with no dish
associations — so only the route move was needed. The build produces **178**
place pages, which is exactly the API's set of places that have dishes.

## 6. The atlas stops drawing relation type `family`

47 of the 82 live connections are `family`. The blueprint says to stop drawing
them.

**The rule is unconditional.** It lives in one place —
`apps/web/src/lib/atlas-filters.ts`:

```ts
export const NEVER_DRAWN = "family";
```

and every kind update goes through it. **A URL parameter cannot re-enable it**:
`?kinds=family` is dropped, and no UI toggle can turn it back on. There is a
test for the URL case and one for the default set.

## 7. The build gate

`validate-build.mjs` was rewritten for the new routes: `/regions`, `/map` and
`/place` are asserted **absent** from `dist/`, `/atlas` and `/places` are
asserted **present**, and a **redirect-drift check** was added — the generator
grew a `--write` mode (it only *printed* its block before, which is why
`nginx.conf` kept serving the old rules) and a `--check` mode that the
validator runs.

`scripts/generate_sitemaps.mjs` now lists `/atlas`, `/places` and the place
pages. The English sitemap carries **1,696** URLs: `/atlas`, `/places`, 178
place pages, and **no** retired route.

**In CI it passes** — this PR's `Tests (vitest + postgis)` job is green, which

### The lint gate caught 14 of mine, and they are fixed

### The map's OWN default must exclude `family` too (`9bb32d9`)

The rail's `family` exclusion was applied to the options the rail BUILDS, but
not to the state the map's OWN default filter is seeded from. The map could
therefore still be seeded with a `family` relation — the one relation the
whole page exists to stop drawing. `atlas-filters.ts` now excludes `family`
from **every** path into the filter state, all five of them, and the two
new tests are proven to FAIL without the fix (reverting the fix fails
exactly those two, 343/345).

### The atlas's counts are derived, not copied (`7fbe2e2`)

The capture carried a hand-maintained `counts` block, and it had gone stale:
the capture's OWN data said **180 places** and **108 communities**, while the
copied block still said **0** and **0**.

A copied number can disagree with the data it describes; a derived number
cannot. The mock now computes the counts from the capture with the SAME
semantics the live route uses (`apps/api/src/routes/atlas-counts.ts`):

| metric | how it is derived |
|---|---|
| `places` | `count(DISTINCT entity_id)` where kind = `place` |
| `communities` | `count(DISTINCT entity_id)` where kind = `community` |
| `connections` | the distinct **undirected** pairs, normalised `LEAST`/`GREATEST` the way the route normalises them |

Two details the test pins, because both are easy to get subtly wrong:

- **ENTITY IDENTITY, NOT NAMES.** The live route counts `entity_id`. Two
  distinct entities share a NAME — the catalogue has two "China" and two
  "Luxembourg" — so counting NAMES reports 178 places where the live API
  reports 180.
- **THE RELATIONSHIP IS PART OF THE KEY.** The route groups by
  `(a, b, relation_type)`, so two relations between the same two dishes are
  two connections: **82 connections over 78 distinct dish pairs**.

**WHAT IT COST, HONESTLY.** No page shipped a wrong number. The two live
consumers of these counts read only `dishes` and `families`, which were never
stale, and `AtlasHeroKpi.astro` turns out not to be mounted anywhere. So the
defect was a **trap**, not a visible outage.

But a stale ZERO is the worst kind of stale. `AtlasHeroKpi.astro` renders a
metric only when its value is non-zero, so a zero **silently drops** the
metric instead of printing a wrong one. The moment anyone mounts that band
or adds a place/community figure, the zeroes would have swallowed two real
numbers the catalogue has — with nothing on the page saying why.

The mock now serves all nine counts **identically** to the live API:
`dishes 1474, places 180, communities 108, families 123, techniques 16,
courses 3, contexts 4, connections 82, claims 0`.

The ten new tests are proven to FAIL without the fix: with the capture stale
again **one** fails, and with the mock serving the copy again **two** fail.

### Not built here, on purpose

- **Timeline** is WP-C4's work. The switcher control is present; the view is
  not.
- The mockup's **"Only claims with a source"** checkbox. The API exposes no
  per-connection source flag — `reason` is free text — so a checkbox over it
  would filter on nothing. WP-C3's acceptance contract does not require it.

### The old paths: one 301 hop, then a 200

Measured on staging, one hop at a time, with the query string carried
through:

| old path | hop 1 | lands on | hop 2 |
|---|---|---|---|
| `/map` | 301 | `/atlas` | 200 |
| `/map?x=1&y=2` | 301 | `/atlas?x=1&y=2` | 200 |
| `/regions` | 301 | `/places` | 200 |
| `/regions?a=b` | 301 | `/places?a=b` | 200 |
| `/place/greece` | 301 | `/places/greece` | 200 |
| `/place/greece?tab=dishes` | 301 | `/places/greece?tab=dishes` | 200 |

and the new paths answer directly, with no redirect at all:
`/atlas` 200, `/places` 200, `/places/greece` 200, `/places/indonesia` 200.

**Two bugs had to be fixed to get here**, both introduced by `34ddb68`:
the generated rule was `location ^~ /place { return 301 /places…; }`, which
(a) drops the slug — `/place/greece` became `/places` — and (b) is a PREFIX
match, so `^~ /place` also matched `/places` and the page redirected to
itself. The generator now emits boundary-anchored regex locations with a
`rewrite … permanent`, which preserves the suffix, keeps the 301 and cannot
swallow `/places` or `/places/*`. Six regression tests live in
`apps/web/src/lib/redirect-rules.test.ts`; each of the four mutations
(original rule, dropped suffix, wrong status code, swallowed `/places`)
fails them.

### The live relationship vocabulary, and the atlas hiding `family`

**The live API still returns `family` connections.** From
`https://api.gustale.com/api/atlas/connections`:

```
82 connections
byRelationship: { family: 47, shared-ingredient: 2, similar-serving: 7,
                   similar_form: 14, similar_technique: 12 }
```

So the vocabulary is intact — the family relations are in the data, not
retired.

**The atlas hides them.** This was measured in a real browser (Chromium
1440×900), against the live-data build, reading MapLibre's own
`queryRenderedFeatures` — the map's post-filter truth — rather than
grepping the HTML, because `/atlas` is client-hydrated and the HTML
ships no connections at all:

```
the API delivered 82 connections, 47 of them family

connections-family      0 rendered features
connections-likeness   29 rendered features
connections-descent     0 rendered features
connections-migration   0 rendered features
TOTAL RENDERED: 29

the map's "connections" source holds 35 features: { likeness: 35 }
```

The source the layer is given contains **35 `likeness` features and not one
`family` feature** — the exclusion happens at the data boundary, before
anything is drawn. The proof is non-vacuous: 29 connection features really
were rendered.

The URL cannot bring them back either:

| URL | family rendered | total rendered |
|---|---|---|
| `/atlas` | 0 | 29 |
| `/atlas?kinds=family` | 0 | 0 |
| `/atlas?kinds=family,likeness` | 0 | 29 |
| `/atlas?kinds=likeness` | 0 | 29 |
| `/atlas?kinds=bogus` | 0 | 0 |

### The filter vocabulary, stated exactly

The five names in the request do not all exist as filters. The live API's
facet vocabulary is:

```
dishes, places, communities, families, techniques, courses, contexts,
connections, claims
```

so the atlas's filters are **family**, **technique**, **course** and the
relationship-kind filter (`kinds`), which are the four in the screenshots.
"served as" is the `course` facet; "ingredient" is not a facet of its own —
ingredients appear through the `shared-ingredient` relationship, whose
kind is `likeness`; "period" is not implemented as a filter.
