### 3. A broken notification failed the deploy (fixed)

The Telegram curl was written with a **double** backslash at the end of each
line. Bash reads that as an escaped backslash, so the trailing backslash is
consumed and the newline ends the command: curl ran with the URL alone and
with the backslash as an argument — which is where
`curl: (3) URL rejected: Bad hostname` came from — and the `-d` fragments
became separate commands. Under `bash -e` the step died there.

Both Telegram steps had it (CI and the Nightly) and both failed identically:

```
curl: (3) URL rejected: Bad hostname
{"ok":false,"error_code":400,"description":"Bad Request: message text is empty"}
##[error]Process completed with exit code 3.
```

A **single** backslash is a real line continuation, and the `||` fallback now
covers the whole curl — a broken notification can never fail a deploy again.

Reproduced in bash: double backslash → exit 3, `URL rejected: Bad hostname`;
single backslash → exit 0.

### 4. The Nightly (#191) — failed every night since 2026-11-02

The `Full integration` job died on its first real step, before it reached the
drift check:

```
ERROR:  role "gustale" does not exist
```

**Root cause.** The reset step does `GRANT ALL ON SCHEMA public TO gustale`,
and a GRANT needs the role to exist. It did not: the service container's
superuser is `postgres` (`POSTGRES_USER: postgres`), so the image creates the
`postgres` role and nothing else.

The role `gustale` is created by `scripts/ci-migration-role.sql`.
**`ci.yml` runs that file. The Nightly never did** — it was not part of the
change that moved the superuser from `gustale` to `postgres` (`fb05999`,
PR #147). The CI was repaired in `ec8c70e`; the Nightly was left with the
half of the change that breaks it.

**Fixed** by adding a `Set up the roles` step to the Nightly, **before** the
reset. Two things are being arranged and they are not independent: the role
must exist for the GRANT to work, and that GRANT is what gives the bot USAGE
on the schema — which the reset drops when it recreates the schema. The role
is a cluster object and survives the reset; the grant is reapplied by the
reset.

**Reproduced on a fresh `postgis/postgis:16-3.4` container with
`POSTGRES_USER=postgres`** (the Nightly's exact condition):

| | result |
|---|---|
| original reset step | `ERROR: role "gustale" does not exist` — rc 3 |
| fixed order | rc 0, `CI_MIGRATION_ROLE_OK=1` present |

The arrangement matches the CI's exactly: on a fresh container the CI
reference order and the fixed Nightly order give the bot **identical
privileges**.
