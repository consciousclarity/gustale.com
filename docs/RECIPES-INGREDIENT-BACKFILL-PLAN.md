**Design authority:** `docs/ADR-007-A1-recipes-confidence-autopublish-contributors-language-urls.md`

**Companion document:** `docs/SOURCE-TIER-LIST.md` (where the S1–S5

## 1. The problem, in numbers

ADR-007's publish gate requires **every** ingredient a recipe names to
be a **published** Atlas ingredient:

```sql
AND EXISTS (SELECT 1 FROM recipe_ingredients ri
             JOIN ingredients i ON i.id = ri.ingredient_id
            WHERE ri.recipe_id = r.id AND i.status = 'published')
```

That is condition 2 of the confidence computation, and it is checked by
`recipe_compute_confidence()` — a recipe whose ingredient is not
published is capped at **medium** and never publishes.

### What is actually there

| fact | value | how established |
|---|---:|---|
| `ingredients` rows, all `published` | **5** | live API, `GET /api/ingredients?limit=50` |
| of those, in use by a dish | **4** — `bechamel`, `eggplant`, `lamb-mince`, `tomato` | live API, `GET /api/dishes/moussaka-greek` |
| of those, unused | **1** — `bechamel-sauce`, a near-duplicate of `bechamel` with `dishCount: 0` | live API |
| `dish_ingredients` rows in the whole database | **4**, all on `moussaka-greek` | live API census of all 1,474 dishes |
| dishes with any ingredient row | **1** of 1,474 | live API census |
| `recipes` rows | **0** | test DB (`gustale_t_ea058a91`, migration-built) |
| `recipe_ingredients` rows | **0** | test DB |
| `ingredient_categories` (the vocabulary) | **435** — 380 with a `foodon_id`, 41 with a parent | test DB |
| `ingredients.category` values set | **0 of 4** — the column is unused | test DB |
| `sources` in `S1`–`S5` | **0** (all 1,486 are `S6`) | repo baseline |
| `source_candidates` | **0** | repo baseline |
| `statements` at `verified`/`published` | **0** of 1,354 | live API: every dish's `evidence.verifiedCount` is 0 |

This matches ADR-007-A1 §3.1 exactly — 5 published ingredients, 4 in
use — and it is the number the owner's brief got wrong ("4" is the number
*used*; the gate counts *published*).

### The arithmetic that makes this urgent

A recipe for nasi goreng names roughly: shallots, garlic, palm sugar,
chilli, rice, banana leaf, tamarind, kecap manis, egg. **Nine ingredients
per recipe, and the whole database has five, none of which is any of
those nine.**

The first wave needs on the order of **150–250 distinct ingredients**
before recipes can be drafted at all (this is an estimate from the recipe
corpus, not a measured number — see §7.3 for how to measure it instead
of estimating it). At 4 `dish_ingredients` rows in the entire live
database, the ingredient table is not merely small; it is **empty for the
purpose of recipes**.

### And the second, harder blocker

Even with the vocabulary in place, **no recipe can reach HIGH**, because:

1. condition 5 requires every core claim to carry a `supports` citation
   from an `S1`–`S5` source — and there are **zero** `S1`–`S5` sources;
2. condition 5a requires that **no** contributing source is `S6`/`S7`;
3. condition 6 requires **≥2 independent** such sources;
4. condition 7′ requires every core claim to carry a citation with an
   exact **locator**;
5. condition 4 requires each claim's statement to already be
   `verified`/`published`, and **the `verified` transition needs a
   human** with a verified publisher credential (`publish_credential` is
   empty).

So the backfill has **two** halves, and the second half is the one that
actually unblocks publication:

```
half 1: the vocabulary   → ingredients exist, so a recipe can name them
half 2: the evidence     → S1-S5 sources exist, so claims can be verified
```

ADR-007-A1 §3.2 chose the honest path for half 1: an ingredient row that
carries only a name, a category and a slug **needs no source**. That is
what this plan implements. Half 2 is `docs/SOURCE-TIER-LIST.md`'s job, and
this plan sequences it against the same gates.

## 3. The stages, and the gate at each

ADR-007-A1 §3.2 names three stages. This plan keeps them, names the gate
at each, and adds the two stages the live data forces (a vocabulary gate
and a publication/sitemap gate).

```
STAGE 0   the vocabulary decision      →  a decision, no write
             GATE 0: the owner approves the category vocabulary
STAGE A   the pantry list               →  a LIST, no write
             GATE A: the owner approves the list
STAGE B   the rows                      →  INSERT ... status='draft'
             GATE B: the owner approves the rows
STAGE C   the publication               →  status='published'
             GATE C: the owner approves publication
STAGE D   the first recipe's evidence   →  the S1-S5 chain for ONE dish
             GATE D: the owner verifies the first statement
```

**The rule that governs all of them:** a stage that is not reviewed does
not advance, and **review happens before the next stage starts**. This is
ADR-007-A1 §3.2's own wording ("the owner approves the stage's output
before the next stage starts"), and it is not negotiable: the whole point
of staging is that a bad vocabulary decision is caught while it is still
a list.

### Who reviews, and what "passed" means

| stage | reviewer | checks | "passed" means |
|---|---|---|---|
| **0** | Alejandro | the category vocabulary is one of the two named in §4.1; the `other` gap is closed or waived | a written decision naming the vocabulary |
| **A** | Alejandro | every name is the canonical name in its language; no ingredient is listed twice under two names; the slug is English, stable, and not already taken | a written approval of the list |
| **B** | Alejandro | every row has name + slug + category from the approved vocabulary; `origin_geo_id` is NULL unless the origin is documented; **no description text** (see §4.3) | a written approval of the rows |
| **C** | Alejandro | the rows are right; the slugs are the ones the recipes will use | a written approval to publish |
| **D** | Alejandro (the only person who can) | the citation carries an exact locator; the source class is right; the claim is `documented` | the statement moves to `verified` — **a human credential, not an agent action** |

## STAGE 0 — the vocabulary decision (no write)

### The problem it solves

`ingredients.category` is a **free-text column with no foreign key**
(`\d ingredients` on the test DB: the only constraints are the primary
key, `slug` unique, and the `origin_geo_id` FK). There are therefore
**three** competing vocabularies in the repo:

| vocabulary | where | size | shape |
|---|---|---:|---|
| the TypeScript union | `packages/db/src/schema/index.ts:252` (`ingredientCategory`) | **12** | `grain, vegetable, fruit, meat, fish, dairy, spice, herb, oil, sweetener, beverage, other` |
| the database table | `ingredient_categories` | **435** | 380 FoodOn-identified + 55 project rows; a 2-level tree (41 are children) |
| the seeded project categories | the 55 project rows | 55 | the project's own slugs, e.g. `savoury`, `noodle`, `wrapper` |

**Measured divergence (test DB):** 11 of the 12 TypeScript values exist
as `ingredient_categories` rows. **`other` does not exist.** Meanwhile
`meat`, `oil` and `vegetable` exist as rows but are **top-level with no
parent** (`has_parent = false`), while the other eight are children of a
parent row — so the same string is a parent in one place and a child in
another.

### The decision the owner has to make

**Which vocabulary does `ingredients.category` use?**

| option | what it means | cost |
|---|---|---|
| **A. the 435-row table** | `ingredients.category` holds a **slug** that must exist in `ingredient_categories` | the 12-value TypeScript union becomes wrong and must be widened or removed; **requires a Drizzle change** (item 4's schema work) |
| **B. the 12-value union** | `ingredients.category` holds one of 12 coarse buckets | loses the FoodOn alignment the vocabulary was built for; 435 → 12 is a big narrowing; the `other` bucket absorbs a lot |
| **C. free text, as today** | no vocabulary at all | the "category is from the existing category vocabulary" review rule in ADR-007-A1 §3.3 cannot be checked mechanically |

**Recommendation: option A.** The 435-row table is the vocabulary the
project actually built (with FoodOn identifiers, a hierarchy, and a
generator script); the 12-value union is a leftover of the pre-FoodOn
design. Option A also makes the review rule checkable: "the category is
from the vocabulary" becomes a lookup instead of a judgement.

**This was a finding to report, not a decision to take.** Under Rule 10
the vocabulary is the owner's. The plan below proceeds on **option A** and
says so, so that the stages are executable, and the decision can change
it before any write.

### Gate 0 — the vocabulary decision — **DECIDED 2026-11-09**

> **The owner's decision, verbatim:**
>
> 1. **Vocabulary: option A**, the 435-row FoodOn table. **No "other"
>    bucket: an ingredient without a fitting category goes to my review
>    queue.**
> 2. **S4: option 1**, library catalogues (WorldCat / LoC records) as the
>    S4 discovery source.
> 3. **Pilot dish: moussaka-greek first**, nasi goreng second.

**So the vocabulary is the 435-row `ingredient_categories` table.** The
12-value TypeScript union is replaced, and `other` **does not exist**:

- there is no `other` row in `ingredient_categories`, and none is created;
- the 12-value union's `other` member is **removed**, not mapped;
- an ingredient whose category does not fit the vocabulary **goes to the
  owner's review queue** — it is not bucketed, and it is not written with
  a null category as a way of hiding it. The review queue is
  `editorial_review_queue` (created by `0052`).

**What this changes in the plan below:**

- **Stage 0** is closed. The Drizzle change (item 4's schema work, now
  its own card) widens `ingredients.category` from the 12-value union to
  the 435-row vocabulary.
- **Gate A** (the pantry list) is unchanged in substance — every category
  it proposes must be a slug from the vocabulary, and one that fits
  nothing goes to the review queue.
- **Stage B** (the rows) still needs the owner's approval of Gate A
  before anything is written.

**The rule that follows from this, and that the reviewers should apply:**
*an ingredient with no fitting category is a finding, not a gap to be
filled with a bucket.* The old union made that gap invisible — `other`
absorbed everything, and the count of ingredients in `other` was never
looked at. That is the thing this decision fixes.

**No database write happens at Stage 0.** If option A is chosen and the
TypeScript union must change, that change belongs to **item 4** (the
Drizzle schema work), not to this card.

## STAGE A — the pantry list (no write)

### What it produces

A **list**, not rows. For each ingredient the first wave of recipes will
need:

| column | what it is |
|---|---|
| `canonical_name` | the name in the dish's own language (ADR-007-A1 §4.1) |
| `slug` | the English, stable, URL identity |
| `category` | from the Stage-0 vocabulary |
| `needed_by` | the dish slugs that require it |
| `source_language` | the language the name is written in |
| `status` | `S1`–`S5` source, or **none** — and if none, the row carries **no description** (§4.3) |

**No database write. No `ingredients` row. Not even a draft.** The
output is a file — a CSV or a Markdown table — that the owner reads.

### How the list is built

**The list comes from the recipes, not from a catalogue.** ADR-007-A1
§3.5 is explicit:

> Recipes are drafted only after Stage C for the ingredients they name.
> Drafting against a vocabulary that does not exist yet is how "palm
> sugar" and "gula aren" end up as two rows.

and §3.2 Stage A:

> Source: the recipes themselves, drafted in draft-only form first.

So the input is a **draft-only recipe corpus**. Item 8 is the drafting
pipeline, but the backfill cannot wait for it — so Stage A needs a
**pilot corpus** of drafted recipes.

**Recommendation: the pilot corpus is the ADR-007-A1 §3.5 first wave.**
The recipe pipeline (item 8) is not built yet, so Stage A's input must
be a **hand-drafted draft-only corpus** for the first wave's dishes —
enough to cover the ingredients they name. This is a real sequencing
constraint and it is worth stating plainly: **Stage A is blocked on
drafted recipes, and the drafted recipes are item 8's output.** The
options are (a) hand-draft a first-wave corpus now as the pilot input, or
(b) run Stage A against an ingredient list derived from the **existing
recipe corpus the project already has**.

For (b): the repo holds **1,381 Pool A dish records** with their
Wikipedia leads in `data/pool_a.json` / `data/pool_a_leads.json` (the
S6 discovery text). Those leads are S6 discovery data, and they *do*
name ingredients in prose ("cooked with kecap manis (sweet soy sauce),
shallots, garlic, tamarind, and chilli"). That is **not** a recipe
corpus and it is **not** a source of truth for a recipe's ingredient
list — but it is a **candidate generator**: it can propose the ingredient
names that the first wave will need, for free, from data already in the
repo.

**Recommendation:** use the Pool A leads to **seed** the candidate list,
then have the pilot's drafted recipes **correct** it. This is a
documented approximation, and Stage A's gate is where the owner confirms
or rejects every name.

### The slug rule (decided at Stage A, not later)

| rule | why |
|---|---|
| the slug is **English** | the slug is the URL identity; ADR-007-A1 §3.3 says "the slug is stable and in English" |
| the slug is the **singular, lowercase, hyphenated** canonical name | `eggplant`, not `eggplants`; `lamb-mince`, not `ground-lamb` |
| a **prepared form** is its own ingredient | `lamb-mince` (minced lamb) is a distinct ingredient from `lamb`; the DB already models this: `ingredients` → `ingredient_variants` (`variant_id` on `dish_ingredients`) |
| a **dish** is not an ingredient | `nasi-goreng` is a dish; the food-material branch's "composite dishes" group was excluded from the vocabulary for exactly this reason (`scripts/curate_ingredients_1f.py`) |
| the slug is checked against the **existing** `ingredients` table before it is proposed | `bechamel` already exists — the list must reuse it, not invent `béchamel-sauce` again |
| the slug is checked against the **`ingredient_categories`** vocabulary | a category slug is not an ingredient slug, but they share a namespace in practice, and the 435-row table contains words like `chili`, `garlic`-like entries that are *categories*; confusing the two is the most likely way to create a duplicate |

### Gate A — the pantry list

- **Input:** the candidate list (Pool A leads seeded, pilot recipes
  corrected), with slugs, categories and `needed_by`.
- **Checked by:** Alejandro, name by name. The questions are the
  §3.2 ones: *"is 'palm sugar' one ingredient or two? is 'shrimp paste'
  its own ingredient?"*
- **Passed when:** every name is approved, every slug is approved, every
  category is from the approved vocabulary, and **no ingredient appears
  twice**.
- **Explicitly not checked here:** the descriptions. A description is a
  claim, and a claim needs a source (§4.3).

## STAGE B — the rows (INSERT, `status='draft'`)

### What it writes

For each approved ingredient:

```sql
INSERT INTO ingredients
  (canonical_name, slug, category, status, created_by, last_edited_by)
VALUES (..., 'draft', ...);
```

and its translation in the dish's own language:

```sql
INSERT INTO ingredient_translations
  (ingredient_id, language, name)
VALUES (..., ...);
```

`ingredient_translations` is keyed `(ingredient_id, language)` and
carries **no source column** — ADR-007-A1 §4 confirms this is correct
("language-first, no source column — no change needed").

### The rules

| rule | source |
|---|---|
| `status = 'draft'` — **never** `'published'` at this stage | ADR-007-A1 §3.2 Stage B |
| `short_description` and `long_description` are **NULL** unless the ingredient carries its own `S1`–`S5` source with a locator | §4.3 below |
| `origin_geo_id` is **NULL** unless the ingredient's origin is itself documented | ADR-007-A1 §3.2 Stage B ("its origin must not be invented either") |
| `scientific_name` only when a taxonomic authority gives it | §5.2 |
| `category` from the Stage-0 vocabulary | Stage 0 |
| `created_by` names the actor that ran the script — **not** a human's credential | the audit trail |
| the slug is **not** renamed afterwards | §4.4 |

### How it is written

**A generated SQL file, reviewed before it runs — not an ad-hoc script.**
The repo already has the pattern: `scripts/curate_ingredients_1f.py`
emits `scripts/emit_ingredients_1f_sql.sql`, which migration `0020`
applies. The backfill should do the same:

1. a generator reads the approved Stage-A list and emits a **single
   `.sql` file**;
2. the file is reviewed like any other migration — with the
   `approved-live` label and a separate go (Rule 1, `docs/RULES.md`);
3. the file is **idempotent**: re-running inserts 0 rows and changes
   nothing, exactly as `0020` is.

**The generator must not run against live by accident.** The repo's own
mechanism for this is `scripts/lib/db_guard.py`, which
`scripts/find_source_candidates.py` resolves once at import time:

```python
DB_NAME = db_guard.resolve_target(
    os.environ.get("GUSTALE_DB_NAME") or db_guard.scratch_database(),
    purpose="find_source_candidates.py",
)
```

The Stage-B generator uses the **same** guard, so its default target is
the scratch database and live requires the explicit opt-in. This is
already the shape of the repo's write path and it should not be
reinvented.

### Gate B — the rows

- **Input:** the generated SQL file, plus the read-back of the rows it
  wrote (on the **test** database first — see §6).
- **Checked by:** Alejandro, against the approved Stage-A list: same
  names, same slugs, same categories, `status='draft'`, descriptions
  empty.
- **Passed when:** the row count equals the approved list's length, every
  slug is unique, every category resolves against the vocabulary, and
  **no description text was written**.

## STAGE C — publication (`status='published'`)

### Why this is a separate stage

Publishing an ingredient is what **unblocks the recipes that use it** —
the publish gate requires `i.status = 'published'`. So publication is
the point of the whole exercise, and it is also the point of no return
for a wrong name: **a published slug is a URL**.

### What it writes

```sql
UPDATE ingredients SET status = 'published' WHERE slug IN (...);
```

and, if the ingredient has its own source-backed description, the
`citations` row that carries it (see §4.3 for the shape and for why the
existing `citations` table can carry it).

### The two properties publication creates

| property | consequence |
|---|---|
| the ingredient's **slug becomes immutable** | `ingredients_published_slug_guard()` refuses a rename |
| the ingredient's **page becomes potentially indexable** | `gustale.recipes/ingredients/<slug>` exists and returns `200` today |

The second one is a **finding**, and it needs a decision:

> The ingredient pages are live and self-canonical, but the recipes
> sitemap contains **no** ingredient URLs (1,531 URLs, zero of them an
> ingredient). So today an ingredient page is reachable and canonical but
> **not listed in any sitemap**.

Publishing ingredients therefore creates pages that search engines can
reach by link but cannot find by sitemap. That is not necessarily wrong —
but it is a deliberate choice, and it should be **the owner's**, not a
side effect of a backfill.

### Gate C — publication

- **Input:** the Stage-B rows, verified as drafts.
- **Checked by:** Alejandro.
- **Passed when:** the rows are published, **and** a decision is recorded
  on the sitemap question (add ingredient URLs to the recipes sitemap,
  or keep them out and say why).

## STAGE D — the first recipe's evidence (the S1–S5 chain)

Stages A–C make a recipe *possible*. They do not make it *publishable*.
Stage D is the first recipe's evidence chain, and it is deliberately
separate because it is the part that has **never been run on real data**.

### The chain

```
a real S1-S5 source  →  a `sources` row with source_class set
  →  a `claim_citations` row (stance='supports', locator, excerpt)
    →  a `statement` about the recipe (subject_type='recipe')
      →  the statement moves research_pending → verified
        →  the recipe's confidence reaches HIGH
```

Each arrow is a mechanism that already exists and has been proved in a
migration proof. What has **never** happened is the first arrow on
**real** data: not one `S1`–`S5` source exists.

### The four mechanical steps

1. **Create the `sources` row** with `source_class` set to the tier the
   publisher earns (`docs/SOURCE-TIER-LIST.md`), plus
   `source_classed_at` and `source_classed_by`. The columns exist
   (`0027`) and are nullable, so an unclassified source is possible —
   and an unclassified source **cannot support a claim**, so a source
   without a class is dead weight.

   > **Note the gap:** `apps/api/src/routes/admin-dishes.ts`'s
   > `POST /api/admin/dishes/:slug/sources` creates a source row and
   > **cannot set `source_class`** — its Zod schema has no such field and
   > the insert omits the column. So the admin write path creates
   > **unclassified** sources, which by definition cannot support a
   > claim. This is a **finding** for the item-4 API work, not something
   > this card changes.

2. **Attach the citation.** `claim_citations` with `stance='supports'`,
   a **non-empty `locator`** (condition 7′), an `excerpt`
   (`excerpt_validated = true`), and `retrieved_at`.

3. **Write the statement** with `subject_type='recipe'` and
   `subject_id = <the recipe's id>`, and link it with `recipe_claims`.
   The scope triggers (PR #203) enforce that a claim names the recipe's
   **own** statement.

4. **Verify it.** `statement_set_status()` moves it to `verified` — and
   this needs **a human with a verified publisher credential**.
   `publish_credential` is empty today, and the auto-publish path is a
   `SECURITY DEFINER` function that acts as `system:auto-publish` with
   **no credential at all**.

### The copy rule, applied to Stage D

ADR-007-A1 §1.4: **published recipe text MUST be in our own words,
never copied.** Concretely, for Stage D:

- the `excerpt` stored in `claim_citations` is **internal only** — it is
  never rendered and never published;
- the recipe's sentence is **written**, not transcribed;
- the citation carries the **locator**, which is what a reader follows;
- the daily digest (§7.3) shows the locator, not the source text.

### Gate D — the first verified statement

- **Input:** the four steps above for **one** claim about **one** recipe.
- **Checked by:** Alejandro — and only Alejandro. The `verified`
  transition is refused for an actor without a verified credential, by
  design.
- **Passed when:** the statement is at `verified`, the recipe's
  `recipe_compute_confidence()` output is `high` (or the next level down,
  with the failing condition named), and the whole chain is reproducible
  from the SQL that produced it.

**Stage D is the real pilot.** A pilot of 30 ingredients that nobody can
publish a recipe with would prove the vocabulary works and nothing else.

## 4. The pilot

ADR-007-A1 §3.5:

```
item 3  ingredient backfill plan  →  Stage A (a LIST, no write)
        owner reviews the list
        item 3 pilot             →  Stage B + C on ~30 ingredients
        owner reviews the rows
        item 8 drafting           →  recipes can now name real ingredients
```

### The pilot, concretely

**Scope: 30 ingredients, one dish, one recipe, one evidence chain.**

| # | what | how many | the gate |
|---|---|---:|---|
| 1 | **the vocabulary decision** | — | Gate 0 |
| 2 | **the pantry list** for **one dish** | ~30 ingredients | Gate A |
| 3 | **the rows** (`status='draft'`) | 30 | Gate B |
| 4 | **publication** | 30 | Gate C |
| 5 | **the first recipe**, drafted against the published rows | 1 | — |
| 6 | **the evidence chain** for that recipe's core claims | ≥2 independent `S1`–`S5` sources | Gate D |
| 7 | **the confidence computation** | 1 recipe | — |

### Which dish

The pilot dish should be:

- a dish **already in the Atlas** with a published page (so condition 1
  passes) — the census shows 1,474 published dishes;
- a dish whose ingredient list is **short enough** to review by hand
  (~30 ingredients is roughly a stew or a braise — a curry or a tagine
  has more);
- a dish whose **language** is unambiguous, so the original-language-first
  rule (§4.1 of the ADR) is not itself a debate;
- a dish whose recipe is **not** a copy of any single published recipe
  (the copy rule is §1.4, and the pilot is where it gets tested).

`moussaka-greek` is the obvious candidate: it is the **only** dish with
ingredient rows today (4 of them), so the pilot continues from the

## 5. The four hard rules

### 5.1 The slug is immutable once published — and the guard is stricter than the ADR says

ADR-007-A1 §3.4 says:

> An **unused** published ingredient (`bechamel-sauce`) is the one case
> where a rename is allowed, because nothing links to it. The guard
> distinguishes those two cases by **link count**, not by a flag.

**The implemented guard does not distinguish by link count. It refuses
every rename of a published ingredient, used or not.** Proved on the
test database (transaction rolled back):

```
BEGIN;
UPDATE ingredients SET slug='bechamel-renamed' WHERE slug='bechamel';
-- ERROR:  the slug of the published ingredient 4d580fde-… may not change
--         from bechamel to bechamel-renamed -- it is part of a published
--         URL. Publish a new ingredient instead.

BEGIN;
INSERT INTO ingredients (canonical_name, slug, status)
  VALUES ('Probe unused','probe-unused','published');
UPDATE ingredients SET slug='probe-unused-renamed' WHERE slug='probe-unused';
-- ERROR:  the slug of the published ingredient 8f2984c2-… may not change
--         from probe-unused to probe-unused-renamed -- it is part of a
--         published URL. Publish a new ingredient instead.
ROLLBACK;
```

The trigger body (`db/migrations/0052_recipes_schema.sql:570-584`) tests
`OLD.status = 'published'` and nothing else.

**Is the implemented behaviour wrong?** **No — it is stricter and safer
than the ADR describes.** The ADR's "unused published ingredient may be
renamed" was a convenience; the implemented rule removes a footgun
(the moment the ingredient is used, the rename becomes illegal, and the
convenience disappears silently). But the ADR and the code **disagree**,
and an ADR is a record of what was decided.

**This is a finding for the owner:**

> **Option 1 (recommended): amend ADR-007-A1 §3.4 to match the
> implemented guard** — a published ingredient's slug never changes, full
> stop, used or not. The `bechamel-sauce` near-duplicate is then handled
> the way the guard already says: publish a *new* ingredient, and either
> retire the unused row or leave it.
>
> **Option 2: implement the ADR's link-count rule** — the guard would
> have to count `dish_ingredients` + `recipe_ingredients` rows. That is a
> schema change to a migration that is **not yet applied to live**, and
> it re-opens a rename path on a published URL.

**Either way, `bechamel-sauce` needs a decision.** It is a published,
unreferenced near-duplicate of `bechamel`, with a live page at
`gustale.recipes/ingredients/bechamel-sauce` returning `200` and a
self-canonical URL. Leaving it is a small mess; removing it is a
deletion of a published URL. **The plan does not touch it** — the pilot's
Stage A list must simply not reuse it, and the owner decides its fate
separately.

### 5.2 The scientific name needs an authority

`ingredients.scientific_name` exists. A scientific name is a **claim**
about a taxon, and taxonomy has **authorities** — which is exactly what
`S3` is for. The tier list's `S3` row names them: GBIF (exact match for
*Solanum lycopersicum* → `usageKey 2930137`, `status ACCEPTED`),
Catalogue of Life, FoodOn.

**Rule:** `scientific_name` is set only when a taxonomic authority
returns it, and the authority's identifier goes into the citation. It is
never typed from memory. `S3` sources are **free** for this purpose —
they are structured APIs with stable ids, and they are the one tier that
can fill the vocabulary's identifiers without a subscription.

### 5.3 A description is a claim; a claim needs a source

ADR-007-A1 §3.3:

> at least one `S1`–`S5` source for the ingredient's own descriptive
> claims | an ingredient description is a **claim**, and a claim with no
> source is worse than no claim

and the recommended path:

> **That second path is the one this amendment recommends.** An ingredient
> row that says only "palm sugar, category: sweetener" is honest, useful,
> and does not need a source.

**The plan implements exactly that.** Stage B writes
`short_description = NULL` and `long_description = NULL` for every
ingredient **unless** it carries its own `S1`–`S5` source with a
locator. In the pilot of 30, the expected number of sourced descriptions
is **0 to 3** — and that is a success, not a shortfall.

**Where a sourced description's citation goes.** The `citations` table is
the existing, working link from a `sources` row to a target
(`source_id`, `target_type`, `target_id`, `claim_text`, `location`). It
has **no CHECK on `target_type`** (verified: `pg_constraint` on
`citations` returns only the primary key and the `source_id` FK), and the
only code that writes it uses `targetType: "dish"`. So:

- `citations` **can** carry `target_type = 'ingredient'` — the schema
  permits it;
- **no code path creates it.** The admin route hard-codes `"dish"`.

**This is a finding for item 4** (the API work), where an
ingredient-citation write path belongs. The backfill plan does not
change it, and Stage B's default of "no description" means the plan does
not **need** it.

### 5.4 The slug is decided once

The Stage-A list is the **only** place a slug is chosen. After that:

- a **draft** ingredient may be renamed freely (the guard only fires on
  `status = 'published'`);
- a **published** ingredient may not be renamed at all (§5.1);
- the recipe pipeline must **look up** the slug rather than derive it —
  `recipe_ingredients` references `ingredients.id`, so a recipe that
  resolves its ingredients by slug at authoring time and stores the id
  at write time is immune to a later rename of a *draft*.

## 6. How the stages are proved, before anything touches live

The repo already has the machinery. `scripts/ci-migration-chain.sh`
builds the whole migration chain on the test Postgres
(`gustale-test-postgres`, `127.0.0.1:5434`) in a database named after
the card, and `scripts/dryrun-migration.sh` runs a migration against a
restored copy of live **on the test container** — never on the
production cluster.

The order for each stage that writes:

1. **Generate** the `.sql` file. It is reviewed as text.
2. **Apply it to the test database** — the card's own
   `gustale_t_ea058a91`, built by the migration chain.
3. **Read it back** with the queries in §8, and compare against the
   approved list.
4. **Prove idempotence**: re-apply; it must insert 0 rows and change
   nothing. (`0020` is written to exactly this standard, and the CI
   checks it.)
5. **Prove the guard fires**: attempt the rename the guard is supposed to
   refuse; it must raise. (§5.1's proof is exactly this.)
6. **Then** the live apply, with the `approved-live` label and a
   separate go (Rule 1).

**Rule 5 applies throughout:** exit codes are captured without a pipe —
`cmd > file; RC=$?` — never `cmd | …; echo $?`.

## 7. Monitoring, and what "done" means for each stage

### 7.1 The read-back queries

These are the checks that every stage ends with. They are written so
that a reviewer can run them without the script.

```sql
-- Stage B: the rows that were written
SELECT slug, canonical_name, category, status,
       short_description IS NULL AS no_short,
       long_description  IS NULL AS no_long,
       origin_geo_id IS NULL    AS no_origin
  FROM ingredients
 ORDER BY slug;

-- Stage C: publication
SELECT count(*) FILTER (WHERE status='published') AS published,
       count(*) FILTER (WHERE status='draft')     AS draft,
       count(*) AS total
  FROM ingredients;

-- the vocabulary check (option A)
SELECT count(*) AS unknown_categories
  FROM ingredients i
 WHERE i.category IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM ingredient_categories c WHERE c.slug = i.category);

-- the description-without-a-source check
SELECT count(*) AS descriptions_without_a_source
  FROM ingredients i
 WHERE (i.short_description IS NOT NULL OR i.long_description IS NOT NULL)
   AND NOT EXISTS (
     SELECT 1 FROM citations ct
      WHERE ct.target_type = 'ingredient'
        AND ct.target_id = i.id);

-- the evidence chain, once Stage D has run
SELECT src.source_class, count(DISTINCT src.id) AS sources
  FROM sources src
 GROUP BY 1 ORDER BY 1;

SELECT count(*) FILTER (WHERE status='verified')   AS verified,
       count(*) FILTER (WHERE status='published')  AS published,
       count(*) FILTER (WHERE status='research_pending') AS research_pending
  FROM statements;
```

### 7.2 The monitoring that matters after the backfill

| metric | where | the threshold that matters |
|---|---|---|
| ingredients published | `ingredients` | — |
| ingredients with a description but no citation | §7.1 | **must be 0** |
| ingredients whose category is not in the vocabulary | §7.1 | **must be 0** |
| `sources` by class | `sources` | `S1`–`S5` must be **> 0** |
| `statements` at `verified` | `statements` | must be **> 0** — this is the gate that is currently unreachable |
| recipes at `high` | `recipe_confidence` | the pilot's target |
| ingredient URLs in the recipes sitemap | the sitemap | the Gate-C decision |

### 7.3 Measuring the ingredient requirement, instead of estimating it

The plan quotes "150–250 ingredients" for the first wave as an
**estimate**. It should not stay an estimate. The measurement is
available and cheap:

```
GET /api/dishes/<slug>   →  the `ingredients` array, per dish
```

Every dish's ingredient list is already in the public API. So the
first wave's requirement can be computed as the **union of the ingredient
sets of the first wave's dishes**, deduplicated. That is a `GET` per
dish, it needs no database access, and it produces the **real** number
that Stage A's list size should be.

**Recommendation: run that union before Stage A**, so Stage A's scope is
measured rather than guessed. It is the same census technique used to
produce the numbers in §1.
