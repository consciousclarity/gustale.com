# How the cut was found

The FoodOn food-material branch (`FOODON:00002403`) holds **20,148**
terms. Most are the wrong thing:

- food **products** (chow mein, egg spread, brownie mix);
- classification **scaffolding** (food material by characteristic, by
  process, by consumer group).

FoodOn imports the **EFSA FOodex2** hierarchy, whose terms carry a
5-digit code in the label (`19100 - mammals meat`). Inside that subtree
there are exactly three levels:

| level | count | what it is |
|---|---|---|
| 0 | 21 | the FOodex2 top-level groups (`00010 - grains and grain-based products`) |
| 1 | **427** | the ingredient **classes** (`19100 - mammals meat`, `05740 - bulb vegetables`) |
| 2 | 1,891 | specific **products** within them (`potato boiled`, `italian corn salads`) |

**Level 1 is the vocabulary.** It is 427 terms — inside the plan's
250–400 target — and each one is a class of thing a dish is made of.
Level 2 is too fine: a dish's ingredient axis records what a dish is
MADE OF, not which cultivar or which preparation.

Six top-level groups are excluded because they are not ingredients:
beverages, water, juices, food for young children, non-standard-diet
products, and composite dishes (**a dish is not an ingredient**).

# The traps, and what they cost

These are worth recording, because each one produced a wrong result
before it was found.

1. **The OLS4 API's hierarchy endpoints do not work for FoodOn.**
   `children` and `hierarchicalDescendants` return 400/404, and the
   `parents` filter silently ignores the ontology — it returned AfPO
   terms for a FoodOn query. The **OWL file** from
   `purl.obolibrary.org` is the reliable source.

2. **The level is NOT the depth.** Depth is a property of the whole
   branch; the EFSA terms sit at depths 4, 6 and 8 while thousands of
   non-EFSA terms sit at depth 5 and 6 too. Selecting "depth 5" pulled
   in 2,793 unrelated terms. The levels must be computed by **BFS from
   the 21 top groups**.

3. **Two key forms.** The class IRIs are `.../obo/FOODON_00002403`
   (underscore); the IDs we publish are `FOODON:00002403` (colon). The
   children map is keyed by the underscore form, so the walk stays in
   that form and converts only on output. Getting this wrong made
   every term look like depth 1.

4. **Definitions are `rdfs:comment` with an `xml:lang` of `en`**, not
   the `IAO_0000115` annotation (which is in the file, but is not how
   these are attached). With the right source, 10,358 of the 20,148
   terms carry a definition.

5. **The project's 55 categories must keep their own slugs.** The
   dishes reference them by id. Mapping `beef` onto a FoodOn row called
   `mammals-meat` would have deleted `beef` and broken every dish that
   uses it. So each project category stays a row, and the FoodOn class
   becomes its **parent**; the class carries the ID, the project row
   carries the project's label and slug. That is exactly the
   "identifiers only, our own labels" split the plan asks for.

6. **A slug can collide.** `vinegar` is both a project category and a
   FoodOn class. One row must win and it must be the **project's**, so
   the FoodOn class row is dropped and its ID is transferred onto the
   project row. That is why the database holds 435 rows for a 434-row
   vocabulary.

7. **Two categories cannot share a FoodOn ID** (there is a partial
   unique index on it). Where two project categories map to the same
   class — `beef` and `red-meat` both → `mammals meat` — the second
   keeps its own slug and simply has no ID of its own.

# The migration

`db/migrations/0020_gus242_ingredient_categories.sql`, generated by
`scripts/emit_ingredients_1f_sql.py` from the curated JSON so the two
can never drift.

- **Pre-flight**: the table exists and is populated; all 54 project
  categories are present; no existing row would have its FoodOn ID
  changed; no FoodOn ID is already held by a different slug.
- **Writes**: 380 inserts (parents before children, because
  `parent_id` is a FK) and 54 `UPDATE`s that set the project
  categories' parent. The project rows' slug, name and description are
  never touched.
- **Post-assertions**: the row count; no FoodOn ID used twice; the
  hierarchy is acyclic; no dangling parent; all project categories
  still present; the dishes' ingredient links are intact.
- **Idempotent**: the guard checks that the data is present AND that
  the migration has not already been applied, so a fresh deploy against
  an already-migrated database skips cleanly.

## One correction worth recording

The acyclicity assertion was wrong on the first attempt and reported
**82 cycles** on a hierarchy that provably had none. The query walked
to each node's parent while excluding any node already in the path —
which stops the walk *before* it can return to its start, so it can
never detect a cycle, while the final `id = ANY(path)` test matches
every row's own starting path. The fix is the same one applied to
migration 0018: compare the walked node against the start with
`lvl > 1`, which distinguishes "arrived back at the start" from "the
first step".

# Decisions

- **decided-by: hermes** — the vocabulary is the 21 FOodex2 groups plus
  the 427 level-1 classes (plus the project's own 54). Reason: the
  plan names the EFSA FOodex2 groups as the source and gives 250–400 as
  the target; level 1 is the only cut that is both the right
  granularity and inside the target.
- **decided-by: hermes** — the project's 54 categories are preserved as
  their own rows with the FoodOn class as their parent, rather than
  being merged into the FoodOn rows. Reason: the dishes reference them
  by id, and a slug rename would silently drop ingredients from dishes.
- **decided-by: hermes** — the six non-ingredient FOodex2 groups are
  excluded. Reason: a dish's ingredient axis records what it is made
  of; a beverage is a course, and a composite dish is a dish.
- **decided-by: hermes** — ten project categories carry no FoodOn ID
  (`coconut`, `meat`, `oil`, `pork`, `poultry`, `red-meat`, `rice`,
  `shellfish`, `vegetable`, `white-meat`). Reason: each maps to a class
  that another category already holds, or to a class that was excluded,
  and the DB forbids a duplicate `foodon_id`. An absent ID is honest; a
  wrong one is not.
